# Contributing to botplate

Thanks for taking an interest in botplate! This is a Rust port of the original
`botplate` Discord bot. Below is a guide on how the project is organized. 

Just some simple rules, Nothin' crazy.

## Ground rules

- **Target the `testing` branch**, not `master`. Active development happens on
  `testing`; `master` lags behind and gets updated in batches if a feature has been tested enough.
- Open an issue for bugs and small fixes/typos. Full feature changes should be a PR.
- One logical change per PR. Please don't bundle an unrelated refactor with a
  bugfix — makes review harder and history messier.
- Run `cargo clippy` and `cargo fmt` before opening a PR. CI will yell at you
  otherwise.
- If your change touches the database, please make sure it works. We assume you know what you're doing.

## Project structure

The codebase is organized by feature/domain:

```
src/
  <feature>/
    mod.rs        -- wires the submodules together
    <feature>.rs  -- the actual poise commands
    helpers.rs     -- logic lives here!
    db.rs          -- (where relevant) database-specific helpers
    README.md      -- short index of what's in a directory
  entities/        -- SeaORM entities
    types.rs       -- database related types for code cleanliness
  events/          -- Discord event handlers
  errors.rs        -- shared Error types (please use these..)
  global.rs        -- misc shared helpers
  main.rs          -- entry file
migration/         -- SeaORM migrations
```

### Commands stay thin, helpers do the work.

This is a pattern throughout the project: a `#[poise::command]`
function should mostly just parse arguments, call into `helpers.rs`, and format
a reply. Business logic — math, cooldown checks, validation, etc. — belongs
in the helper functions so it's reusable outside of a Discord context. (WebUIs, If I may?)

```rust
// good example: command is thin, logic is handled seperately.
#[poise::command(prefix_command, slash_command)]
pub async fn daily(ctx: poise::Context<'_, crate::Data, Error>) -> Result<(), Error> {
    let author = ctx.author();
    let last = helpers::last_daily(author.id.get() as i64, &ctx.data().database).await;
    if !helpers::can_claim_daily(last) {
        ctx.say("you already claimed your daily today!").await?;
        return Ok(());
    }
    helpers::edit_balance(author.id.get() as i64, 100, &ctx.data().database).await?;
    // ...
}
```

The reason for this is to keep botplate flexible. (We plan to have an API so extensions can be written in other languages.)

If you find yourself writing SeaORM logic directly inside a command function, stop and move it into `helpers.rs`. (or `db.rs` if the logic in helpers is not very clean.)

### Adding or changing database schema

All schema changes go through a migration in `migration/src/`, added to the
`migrations()` list in `migration/src/lib.rs` **in the correct order** —
migration run order matters here (e.g. `central_bank` → `users` → `channels`
→ `items` → `inventory`, since later tables have FKs into earlier ones).

```sh
sea-orm-cli migrate up --database-url sqlite://example.db
```

After writing the migration, regenerate entities as below. Please note in your PR description any design reasoning behind schema choices so reviewers aren't left guessing what the new schema does.

### Entities are generated, not hand written.

Files under `src/entities/` are generated via `sea-orm-cli` from the current
migration state and are marked as such in their header comment
(`@generated by sea-orm-codegen`). Please don't hand-edit them. Regenerate instead:

```sh
sea-orm-cli generate entity -o src/entities
```

The one exception (kind of) is `src/entities/types.rs`, which is a hand-written file of
type aliases kept separate specifically so it survives regeneration.

## Commit / PR style

- Descriptive commit messages > cute ones. You can add a bit of ✨pazzaz✨ to your commit messages.. but please keep it concise and to the point. We enjoy sarcasm but not too much.
- In the PR description, call out:
  - what your commit changes, fixes, or diverges from
  - any database changes (if applicable)
  - anything you're unsure about / want a second opinion on
- Versioning follows SemVer starting at `0.1.0`; `1.0.0` is reserved for full new release.
- You generally won't need to bump version numbers yourself, Maintainers will handle it.

## Development Setup

To set up the development environment, follow these steps:

I'll assume you already have rustup installed, If not:

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
```

(assuming you're using a Unix like system. If not, see [rustup's installation guide](https://rustup.rs/))

1. Clone the repository:

```sh
git clone https://github.com/tuxzilla/botplate.git
```

2. Install dependencies:

```sh
cargo build
```

3. Read this guide!

Wow, look at you! You're already doing that!

4. Create a local database

We use SQLite, so just name a file 'botplate.db' (or whatever.) and point your .env file to it.

(if you need an example of an .env file, see [.env.example](https://github.com/tuxza/botplate/blob/main/.env.example))

5. Run SeaORM migrations:

```sh
sea-orm-cli migrate up --database-url sqlite://botplate.db?mode=rwc
```

6. Start working!
